# Agents Guide — jsonc

## What this project is

`@tabnas/jsonc` is a **JSONC (JSON-with-comments) grammar plugin** for the
[`tabnas`](https://github.com/tabnas/parser) parsing engine. JSONC is a
superset of JSON that adds single-line (`//`) and block (`/* */`)
comments, with **optional** trailing commas in objects and arrays. It is
the format used by VS Code config files (`tsconfig.json`, `settings.json`).

It is **not** standalone: it layers on the
[`@tabnas/jsonic`](https://github.com/tabnas/jsonic) base grammar (the
relaxed-JSON `val`/`map`/`list`/`pair`/`elem` rules) and reuses the
engine's lexer, comment handling, and end-of-input handling. The plugin
adds no rules of its own — it installs a few extra **alts** on jsonic's
existing rules (an end-of-input `#ZZ` alt on `val`, and trailing-comma
alts on `pair`/`elem`) and tightens the lexer/number/string/map options
toward standard JSON. Two plugin options switch behavior: `disallowComments`
(strict JSON, no comments) and `allowTrailingComma`.

There are two implementations that must behave identically — TypeScript
(canonical) and a Go port.

## The tabnas engine dependency

Both runtimes depend on the unpublished `@tabnas` siblings via a
**sibling checkout** (the standard tabnas dev model until the packages
publish tagged releases):

- TypeScript: `@tabnas/jsonic` and `@tabnas/parser` are declared as
  `peerDependencies` (`">=2"`) in `ts/package.json` and mirrored as
  `file:../../jsonic/ts` / `file:../../parser/ts` devDependencies for
  local builds (npm >=7 / Node >=24 auto-installs peers; `engines.node`
  is `">=24"`). `@tabnas/debug` and `@tabnas/railroad` are dev-only
  `file:` devDependencies — debug for the `debug-model.test.ts` composition
  test, railroad to regenerate `ts/doc/grammar.{svg,txt}`.
- Go: `go/go.mod` requires `github.com/tabnas/jsonic/go` with
  `replace github.com/tabnas/jsonic/go => ../../jsonic/go`. `jsonic/go`
  re-exports the engine types (`jsonic.Make`, `jsonic.Options`,
  `jsonic.Jsonic`, …), so `jsonc.go` imports `jsonic`, not `parser`,
  directly. The other replaces in `go.mod` (`parser`, `json`, `debug`)
  cover the **indirect** modules jsonic pulls in transitively; jsonc has
  no direct dependency on them.

Clone the siblings (`parser`, `jsonic`, plus `debug`/`railroad` for the
optional test and diagram) next to this repo and build their TS first. CI
does this for you (see below).

## Authority and alignment rules

**TypeScript is canonical. Go is a port of it.** When you change behavior:

1. Change `ts/src/jsonc.ts` first (or `ts/jsonc-grammar.jsonic` for grammar
   changes — see the embed section below).
2. Port the same change to `go/jsonc.go`.
3. Mirror the test cases across `ts/test/jsonc.test.ts` and
   `go/jsonc_test.go` — the two unit suites cover the same ground (they
   share the microsoft/node-jsonc-parser-derived cases) and both must stay
   green.

Do not let the Go behavior drift from TS. Known accepted deviations are
noted in the test files (e.g. `go/jsonc_test.go` `TestStrings` notes that
jsonic/go's string matcher still accepts `\v` as a built-in escape, which
the TS side rejects via `escape: { v: null }`).

## The grammar is embedded — never hand-edit the embedded block

`ts/jsonc-grammar.jsonic` is embedded verbatim into **both**
`ts/src/jsonc.ts` and `go/jsonc.go`, between these markers:

```
// --- BEGIN EMBEDDED jsonc-grammar.jsonic ---
...
// --- END EMBEDDED jsonc-grammar.jsonic ---
```

Edit `ts/jsonc-grammar.jsonic`, then run the embed step. Never edit the
text between the markers by hand — it will be overwritten. (The grammar
may not contain backticks; `embed-grammar.js` aborts if it does, since the
Go side embeds it as a raw string. Note the TS embedder also escapes `\`,
`` ` ``, and `${`, so the `\\.` in the number `exclude` option becomes
`\\\\.` in the TS template literal but stays `\\.` in `jsonc-grammar.jsonic`
and `go/jsonc.go`.)

```bash
cd ts && node embed-grammar.js   # writes into ts/src/jsonc.ts AND go/jsonc.go
```

`npm run build` runs the embed step first (`node embed-grammar.js && tsc
--build src test`), so a normal TS build keeps both files in sync.

## Architecture notes

- The grammar text is parsed by a **separate** jsonic engine instance
  (`new Tabnas().use(jsonic).parse(grammarText)` in TS; `j.GrammarText` in
  Go), then handed to `tn.grammar(...)` / `j.GrammarText(...)` with
  `{ rule: { alt: { g: 'jsonc' } } }`. That setting tags every alt the
  plugin installs with the group `jsonc`, which the `rule.include/exclude`
  filter and the railroad legend key off.
- The embedded grammar does three things: it sets **static options** that
  pull jsonic toward standard JSON (`text.lex:false`, `number` non-decimal
  bases off + `exclude` of leading-dot numbers, `string.chars:'"'` with
  `escape.v:null`, `map.extend:false`, `lex.empty:false`,
  `rule.finish:false`), adds a `#ZZ` (end-of-input) alt on `val.open` so a
  trailing-trivia-only / empty-ish document resolves, and adds
  `#CA #CB` / `#CA #CS` trailing-comma alts (group `comma`) on `pair.close`
  / `elem.close`.
- **Runtime, argument-dependent** options are applied **in code after**
  `grammar(...)` / `GrammarText(...)`, not in the embedded text:
  `comment.lex` is toggled by `disallowComments`, and `rule.include`
  (`'jsonc,json'`) keeps the plugin + base alts while `rule.exclude` is set
  to `'comma'` unless `allowTrailingComma` is passed (which leaves the
  `comma`-group trailing-comma alts active). Order matters — Grammar runs
  an internal `SetOptions`, so applying these after it avoids clobbering.

## Build & test

TypeScript (from `ts/`):

```bash
npm install            # auto-installs the jsonic/parser peers; resolves file: siblings
npm run build          # embeds grammar, then tsc --build src test
npm test               # node --test over dist-test/*.test.js
```

`npm test` has a `pretest` hook that runs
`scripts/fetch-conformance-suites.sh` first, so the corpora are always in
place — including in CI, whose ts job runs `npm test`.

The TS suite is: `jsonc.test.ts` (unit, incl. the microsoft cases and the
`alt g jsonc tag` introspection check), `conformance.test.ts` (the derived
JSONC corpus — expected red, see below), `jsontestsuite.test.ts` (the RFC
corpus in strict mode), `parity.test.ts` (the shared `test/spec/*.tsv`
fixtures), `debug-model.test.ts` (the `@tabnas/debug` composition),
`doc-examples.test.ts` (runs `// =>` assertions extracted from the READMEs —
keep doc examples correct), and `perf.test.ts`.

Go (from `go/`):

```bash
../scripts/fetch-conformance-suites.sh   # REQUIRED FIRST — see below
go build ./...
go test -v ./...       # jsonc_test.go (unit, mirrors the TS unit cases),
                       # conformance_test.go + jsontestsuite_test.go (both
                       # expected red — see the conformance section),
                       # parity_test.go, perf_test.go
```

`go test` has no pre-hook, so the fetch is not automatic on the Go side. The
Go conformance tests FAIL with fetch instructions when the corpora are absent
— they never skip. `make test` and `make test-go` run the fetch for you.

The repo-root [`Makefile`](Makefile) wraps both halves: `make build|test`
run the TS and Go sides, and `make publish-go V=x.y.z` injects `V` into the
`const Version` in `go/jsonc.go` (currently `0.1.2`), commits, and tags
`go/vX.Y.Z`. `make publish-ts` publishes the TS package at its
`package.json` version (currently `0.8.0`). `ts/Makefile` has the same
targets scoped to the package, plus a standalone `make embed`.

Local builds resolve the unpublished siblings without a workspace file:
the TS side via the `file:../../{jsonic,parser,debug,railroad}/ts`
devDependencies in `ts/package.json`, and the Go side via the `replace`
directives in `go/go.mod` (`../../jsonic/go`, plus the transitive
`parser`/`json`/`debug` replaces). There is no checked-in `go.work`.

## Conformance suites — both are EXPECTED TO BE RED

Two conformance suites run in **both** runtimes. They are measuring
instruments, not targets. Never add a skip list, narrow a corpus, or weaken an
assertion to raise a number: a conformance figure that cannot fail is worth
nothing.

**Neither corpus is committed.** `scripts/fetch-conformance-suites.sh` fetches
them at pinned commit SHAs into the gitignored `test/vendor/`. If they are
absent the tests **FAIL LOUDLY** with fetch instructions — they never skip.
Before 2026-08 `ts/test/jsontestsuite.test.ts` silently skipped when the corpus
was missing, which is the same defect class as a swallowed failure.

### `test/vendor/corpus.json` (491 cases, derived)

`ts/test/conformance.test.ts` and `go/conformance_test.go` run the same corpus.
A valid case must parse **and** produce the reference implementation's value;
an invalid case must be rejected with an error. Provenance:

-  48 `upstream-assertion` — input, verdict AND value hand-written in
   microsoft/node-jsonc-parser's own `src/test/json.test.ts`
- 408 `reference-oracle` — input from that file's other helpers or from
  nst/JSONTestSuite (318 files); verdict/value computed by RUNNING the
  reference implementation compiled from its pinned commit
-  35 `leniency-probe` — inputs taken from `@tabnas/jsonic`'s own README
  "The relaxations"; verdicts still from the reference

The generator cross-checks every upstream-authored verdict against the shipped
implementation and aborts if they disagree. Independent corroboration: the
oracle agrees with JSONTestSuite's own `y_`/`n_` labels on 280 of 283 decided
files, and the 3 disagreements are exactly the comment cases where JSON and
JSONC are supposed to differ. Corpus size and every origin subset are pinned by
assertion in both runtimes, so the corpus cannot be narrowed.

Baseline read on 2026-08-07 (branch `conformance-2026-08`), parser untouched:

| | TS | Go |
|---|---|---|
| valid accepted with correct value | 205/205 (100.0%) | 198/205 (96.6%) |
| invalid rejected | 238/286 (83.2%) | 251/286 (87.8%) |
| base-grammar leniency probe | 22/35 (62.9%) | 28/35 (80.0%) |

The dominant failure mode is base-grammar leniency leaking through. The plugin
adds **no rules of its own** — `new Tabnas().use(Jsonc)` alone rejects
everything, even `{"a":1}` — so the documented stack `.use(jsonic).use(Jsonc)`
means jsonic's relaxations are the plugin's relaxations unless explicitly
tightened. In TypeScript the leaks currently include `#` hash comments, `\xNN`
and `\u{...}` escapes, `+1` / `01` / `5.` / `0.e1` numbers, and a second
top-level value being silently discarded (`1 2` parses to `1`).

### JSONTestSuite in strict mode

`ts/test/jsontestsuite.test.ts` **and** `go/jsontestsuite_test.go` run the
nst/JSONTestSuite corpus against the plugin in **strict mode**
(`disallowComments: true`, no trailing commas), classifying each
`test_parsing/*.json` file by prefix: `y_*` must accept, `n_*` must reject,
`i_*` is implementation-defined by RFC 8259 and is checked against the JSONC
reference implementation's verdict recorded in the shared corpus.

Because jsonic is intentionally lenient in spots vs. strict RFC 8259, the cases
jsonic accepts that the RFC rejects are **pinned** in
`test/known-lenient.json` — shared by both runtimes, one written reason per
entry. The test fails if that set grows or shrinks, so update it deliberately
when a lenience genuinely changes; don't re-pin to make it green. Because the
pin records what canonical TypeScript accepts, a Go run that rejects a pinned
case reports it as a TS/Go divergence (there are currently 7).

Before 2026-08 the RFC corpus ran in TypeScript only — the Go port had never
been measured against it at all — and the TS `i_*` block computed a
classification for every file and then asserted only `results.length > 0`.

## Optional composition test (@tabnas/debug)

`ts/test/debug-model.test.ts` composes the jsonc plugin with the external
[`@tabnas/debug`](https://github.com/tabnas/debug) plugin and asserts the
structured grammar model: the rule set is exactly the shared jsonic
`val`/`map`/`list`/`pair`/`elem` (jsonc adds **no** rules of its own),
`m.config.start === 'val'` (note `config.start`, not `m.start`), the plugin
stack is `['jsonic', 'Jsonc', 'Debug']`, `val` pushes `map`/`list`, and the
`map -> pair`, `list -> elem`, `pair/elem -> val` push edges plus the
`pair`/`elem` close-replace self-loops hold. It resolves debug dynamically;
`@tabnas/debug` is a declared devDependency, so if it cannot be required the
test **FAILS** with instructions rather than skipping (it used to skip, which
let a missing dependency hide the whole composition check). `TABNAS_DEBUG_PATH`
points it at a built sibling. There is no Go composition test;
`@tabnas/debug/go` is only an indirect module dependency.

## CI

`.github/workflows/ci.yml` delegates to the org-standard reusable workflow
`tabnas/.github/.github/workflows/polyglot-ci.yml@main` with
`deps: "parser debug json abnf railroad jsonic"`. It has two jobs, neither
publishing to npm:

- **ts** (Ubuntu/Windows/macOS, Node 24): sets
  `git config --global core.autocrlf false`, git-clones the tabnas closure as
  siblings, `npm i && npm run build --if-present` each in topo order, then
  `npm test` in `jsonc/ts`. Because `ts/package.json` has a `pretest` hook
  that runs `scripts/fetch-conformance-suites.sh`, **the corpora are fetched
  before the TypeScript tests run here**. Because `@tabnas/debug` is a
  devDependency, the composition test runs as part of `npm test`.
- **go** (Ubuntu/macOS, Go 1.24): clones the same siblings, sets up a
  `go work`, then `go build ./...` / `go test -v ./...` in `jsonc/go`. This
  job runs `go test` directly, so there is no hook to fetch the corpora — the
  Go conformance tests fail loudly there rather than skipping.

`.github/workflows/conformance.yml` (this repo's own) closes that gap: it
fetches the corpora explicitly **before** running either runtime, and hard-fails
if the fetch did not land 318 RFC files plus the derived corpus. Only the two
conformance *measurement* steps carry `continue-on-error`, because the suites
are expected to be red until phase 2; every other step is hard. Do not extend
`continue-on-error` to cover a broken harness.
